# Shared platform connections

All agent workspaces can inspect the same owner-level Facebook, Instagram, Meta Ads, Google Ads and YouTube adapters. No duplicate credentials or secrets are passed to browser agents or model prompts. These are global platform-owner accounts; this does not authorize another tenant to use INTECA accounts.

The server performs one read-only identity check at startup and exposes refresh through the existing signed administrator session and advertising action header. Concurrent refreshes coalesce. Evidence expires after 15 minutes and is invalidated when provider environment variables change. No publishing, spending, discount, OAuth permission grant or test message occurs during verification. Logs contain channel, fixed state and timestamp only.

GET `/api/advertising/shared-connections` returns current sanitized evidence. POST `/api/advertising/shared-connections/verify` refreshes all five channels. Every runtime manifest entry references that shared evidence. Configured credentials no longer cause an untested runtime agent to be labeled operational.

This is shared connection access and diagnostics, not an implementation of every advertised agent tool. Existing publishing, campaign, sales and enrollment actions continue through their server-side modules and approval rules. Reading an account does not prove billing, lead webhook delivery, paid conversion attribution, campus enrollment or official fiscal issuance. Those must be tested separately against the configured service.

## Owner reconnection

`/api/advertising/oauth/configuration` lists the exact callback URLs and requested scopes, without secrets. The shared agent panel provides Meta, Google Ads and YouTube reconnection. Register the callback in the corresponding **web application** OAuth client first. Meta also requires the Facebook Login use case and any required app review; Google requires the relevant APIs and consent configuration. The CRM cannot self-approve these provider requirements.

POST `/:provider/start` requires the existing signed owner session, advertising action header, callback-registration confirmation and permission review. OAuth uses a random ten-minute, single-use state bound to the browser's signed CRM session and a Secure, HttpOnly, SameSite=Lax cookie; Google also uses PKCE. Destination/client changes invalidate pending authorizations. Pending state is process-local and intentionally lost on restart, so restart requires starting the flow again. At most 20 flows can be pending per server process.

The callback exchanges authorization codes on the server. Meta obtains long-lived user and existing Page tokens; Google obtains scoped refresh tokens. It verifies the existing configured account/channel identities before writing credentials to Render, then updates runtime values and refreshes shared evidence. Credentials never appear in frontend responses, URLs generated by the CRM, logs or model prompts. Native OAuth authorization codes necessarily arrive at the server callback, which returns no-store/no-referrer responses and redirects to a clean URL on success.

Meta uses separate Render writes for Page and Ads tokens. A persistence failure can leave a partial provider configuration; the CRM explicitly reports this and does not report success or switch runtime credentials. Repeat the authorization after fixing persistence. No automatic redeploy is required to apply the renewed runtime tokens; Render stores them for the next restart. No token grant or live provider authorization has been verified merely by passing mocked tests.

The reconnection flow authorizes account access; campaign publication, discounts and spending retain their approval rules. It does not configure campus credentials, SMTP/Resend, DGII certificates, ad billing or paid conversion attribution.
